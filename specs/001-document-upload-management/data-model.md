# Data Model: Document Upload and Management

## Document

Represents metadata for one uploaded file.

| Field | Type | Rules |
|---|---|---|
| DocumentId | `int` | Primary key; generated by the database |
| Title | `nvarchar(200)` | Required, non-empty |
| Description | `nvarchar(2000)` nullable | Optional |
| Category | `nvarchar`/text | Required; one of the stakeholder categories |
| Tags | `nvarchar(1000)` nullable | Optional custom tags |
| OriginalFileName | `nvarchar` | Display-only name; never used as a physical path |
| StoragePath | `nvarchar` | Required portable relative path; generated internally and unique |
| UploadedAtUtc | `datetime2` | Required UTC timestamp |
| UploadedByUserId | existing user key type | Required owner relationship to `User` |
| FileSizeBytes | `bigint` | Required; greater than zero and at most 26,214,400 bytes (25 MiB) |
| ContentType | `nvarchar(255)` | Required; supports MIME values up to 255 characters |
| ProjectId | Deferred until project story | Not present in the P1 schema; add only after the existing project key is confirmed |
| TaskId | Deferred until task story | Not present in the P1 schema; add only after the existing task key is confirmed |

## Future entities

- **DocumentShare:** document-to-user/team access grants for the later sharing story.
- **DocumentActivity:** upload, download, delete, and share events for later reporting.

## Relationships

- `User` 1-to-many `Document` through `UploadedByUserId`.
- Project and task relationships are intentionally deferred until the later stories identify the existing key types; P1 has no project/task foreign keys.

## Validation and invariants

- P1 documents have no project or task association and are visible only to their owner.
- A multi-file request is atomic: every file and its metadata must validate before any file is persisted.
- The storage path is generated from trusted identifiers and a GUID; user input is limited to display metadata and a validated extension.
- File persistence precedes metadata persistence. If metadata persistence fails after a file save, the service deletes the newly saved file.
- Replacing or deleting files must apply the same authorization and storage-boundary rules.
